## CLI commands

| Command | Description | Exit code |
| --- | --- | --- |
| `momo build` | Read the nearest `momo.config.*` and build the current package | Success `0` / error `1` |
| `momo doctor` | Inspect build configuration, dependency rules, and local artifacts without writing | No errors `0` / errors `1` |
| `momo topology` | Run package build scripts sequentially in workspace dependency order | Success `0` / graph or argument error `1` / build failure forwards its exit code |
| `momo help` / `-h` / `--help` | Display help | `0` |
| *(no command)* | Display help | `1` |

`momo build` and `momo doctor` accept `-c, --config <path>` to specify a configuration file. Relative configuration paths resolve from the current working directory. Otherwise, the CLI searches upward for `momo.config.ts`, `momo.config.mts`, `momo.config.js`, or `momo.config.mjs`. Paths inside build configuration resolve relative to the configuration file's directory.

```bash
momo build
momo build -c packages/host/momo.config.ts
momo doctor
momo doctor --json -c packages/host/momo.config.ts
momo topology --filter './packages/*'
momo topology --filter '@momots/drive' --dry-run
momo --help
```

## Configuration

`defineConfig` returns configuration unchanged and provides type inference and completion:

```ts
import { defineConfig } from '@momots/cli';

export default defineConfig({
  build: {
    src: 'src',
    outdir: 'dist',
    format: 'esm',
    target: 'browser',
    packages: 'external',
    splitting: false,
    scripts: ['typecheck', 'types'],
    assets: {
      'assets/tailwind.css': 'tailwind.css',
    },
    executables: [],
  },
});
```

| Field | Default | Description |
| --- | --- | --- |
| `src` | `src` | Source directory |
| `outdir` | `dist` | Output directory |
| `format` | `esm` | `esm`, `cjs`, or `iife` |
| `target` | `browser` | `browser`, `bun`, or `node` |
| `packages` | `external` | Externalize or bundle dependencies |
| `bundle` | `[]` | Package names to inline; these are bundled and other declared dependencies remain external |
| `external` | `[]` | Additional package names to keep external |
| `splitting` | `false` | Extract shared chunks for multiple ESM entries, preserving reference identity across entries |
| `banner` | — | Text prepended to each JavaScript output, such as `'use client';` |
| `scripts` | `['typecheck', 'types']` | Package scripts executed before building |
| `assets` | `{}` | Static files copied after building; keys are relative to the package root, values to `outdir` |
| `executables` | `[]` | Relative paths marked executable after building |

The builder recursively collects `.ts` and `.tsx` files in `src`, ignoring declarations, `*.test.*`, `*.spec.*`, and `*.fixture.*`, and preserves the directory structure in output.

## Workspace topological builds

Topological order builds dependencies before their consumers. `momo topology` searches upward for a `package.json` declaring `workspaces`, collects workspace members, and runs each package's existing `bun run build` sequentially in dependency order. Each package's `scripts.build` still determines its build behavior.

```bash
# Build all workspace members
momo topology

# Select library packages and their upstream dependencies
momo topology --filter './packages/*'

# Select one package from any subdirectory; include its upstream dependencies automatically
momo topology --filter '@momots/drive'

# Display the order without running scripts
momo topology --filter './packages/*' --dry-run
```

`--filter` (`-f`) matches package names or path globs relative to the workspace root. Repeat it to select the union of matches. Quote globs to prevent shell expansion. All local upstream dependencies are included recursively, even outside the filter; each package runs once. A filter matching no packages is an error. Command-line filters do not support `!` exclusions.

The graph reads `dependencies`, `devDependencies`, `peerDependencies`, and `optionalDependencies`. A dependency name matching a workspace package establishes build order without requiring `workspace:*`; for example, a normal peer version range from `host` to `core` still requires building `core` first. This command establishes local build relationships by name, without resolving versions or installing dependencies.

Workspace declarations support path arrays and `{ "packages": [...] }`, including `!` path exclusions. The root package is excluded to avoid calling the root build script again. Packages without a build script participate in ordering and appear as skipped; their upstream dependencies are still processed.

Before running, the command checks duplicate names, invalid manifests, cycles in the selected graph, and missing explicit `workspace:` dependencies. Cycle errors include the complete cycle. Scripts run only after validation; the first failed build stops execution and returns its exit code. Recursive `momo topology` calls inside build scripts fail to prevent infinite recursion.

The current repository root `build` script is:

```json
{
  "scripts": {
    "build": "bun run ./packages/cli/src/bin.ts topology --filter './packages/*'"
  }
}
```

Starting from CLI source allows builds before `dist` exists. The current graph automatically produces `cli → core → host → design → drive`; adding packages or changing dependencies requires no manual build-chain edits. The root build selects only library packages, not examples or the website. Sequential execution avoids downstream reads while an upstream package cleans its declarations from `dist`.

## Local diagnostics

`momo doctor` checks whether the current package can build with its configuration and whether existing artifacts match it. It does not invoke builds or package scripts, install dependencies, or create, clean, or repair files. Like other commands, it executes top-level configuration code, so use trusted configuration without top-level side effects; avoid configuration output to stdout when using `--json`.

Checks include:

- Runtime types and values of `build` fields; unknown top-level and build fields produce warnings;
- Whether build scripts are declared in `package.json#scripts`; defaults are `typecheck` and `types`;
- Conflicts between `bundle` and `external`, including external wildcards and package subpaths; undeclared bundled packages warn, while declarations in `devDependencies` count;
- Whether the source directory and build entries exist;
- Whether outdir overlaps the package root or source, and whether asset destinations or executables escape outdir; existing symlinks are resolved;
- Whether asset sources are files and would be deleted by build cleanup;
- Existing executable outputs and their permissions;
- Whether file targets in package exports exist, including nested conditions and arrays; wildcard targets must match at least one file.

If outdir does not exist, doctor emits one warning and defers checks of exports and executables inside it. Run `momo build`, then diagnose again to check those files. With an existing outdir, missing exports or executables are errors; an outdir outside the package produces a cleanup-scope warning. Builds with `scripts: []` and no nonempty `bundle` can omit `package.json`.

Errors produce exit code `1`; no errors produce `0`, even with warnings. `momo doctor --help` displays help, and `--json` writes a structured report to stdout:

```json
{
  "root": "/workspace/packages/example",
  "config": "/workspace/packages/example/momo.config.ts",
  "ok": true,
  "summary": { "errors": 0, "warnings": 1 },
  "diagnostics": [
    {
      "severity": "warning",
      "code": "output.missing",
      "message": "Output directory does not exist; run momo build before checking artifacts.",
      "path": "/workspace/packages/example/dist"
    }
  ]
}
```

Each diagnostic includes `severity`, `code`, `message`, and an optional `path` for the relevant file or configuration field. `ok` means there are no errors; `config` is `null` if configuration is not found. Configuration loading failures and invalid arguments use the same report shape. CI can use exit codes or handle specific issues by `code`.

doctor checks only local configuration and files, not published file lists, dependency installation, or runtime imports.

## Browser testing

The CLI does not provide a test runner. Non-browser tests use `bun:test` with `*.test.ts`; browser tests use Playwright Test with `*.spec.ts`. Both live beside source files, without a dedicated test directory.

The root `playwright.config.ts` configures browser projects, server startup, and execution options; `momo.config.ts` continues to handle builds. Bun excludes `*.spec.ts` to avoid running Playwright cases. See the [browser testing tutorial](/docs/cli/tutorial) for commands.
