`useControllableValue` implements components supporting both `value` and `defaultValue`: component interactions use one setter to request a value, while callers choose who stores state.

## Why use it

A quantity picker may manage itself in a product preview, while a cart parent must enforce stock limits and reset it alongside other order fields. Date pickers, switches, and popup state face the same issue.

Reimplementing `useState`, `value` detection, and `onChange` in every component quickly exposes these details:

| Problem | Hook convention |
| --- | --- |
| One component must work alone or under form control | Stores internal state when uncontrolled, reads parent values when controlled; interactions share one setter |
| Parent must validate, adjust, or reject input | Setter makes a request; the controlled UI always displays the parent's returned value |
| Successive field updates overwrite earlier changes | Functional updaters read the preceding request result in call order |
| Empty `undefined` is mistaken for an omitted value | `controlled: true` explicitly assigns ownership to the parent |
| Changed defaults or asynchronously supplied values behave unexpectedly | Defaults initialize only once; control mode is fixed on first render |

Use `useState` when state belongs entirely to one component. Use this hook when different callers need to manage the same component's state.

## Scenario 1: One component, two state owners

Component authors pass props to the hook and handle interactions through the returned setter:

```tsx
import { useControllableValue } from "@momots/design/hooks";

type CounterProps = {
  value?: number;
  defaultValue?: number;
  onChange?: (value: number) => void;
};

function Counter({ value, defaultValue = 0, onChange }: CounterProps) {
  const [current, setCurrent] = useControllableValue({
    value,
    defaultValue,
    onChange,
  });

  return (
    <button onClick={() => setCurrent((previous) => previous + 1)}>
      Quantity: {current}, click +1
    </button>
  );
}
```

For standalone usage, provide only an initial value. The hook stores subsequent quantities; adding `onChange` alone does not make it controlled:

```tsx
<Counter
  defaultValue={1}
  onChange={(next) => console.log("Quantity change requested", next)}
/>
```

For form-wide management, store state in the parent. These counters share a quantity; operating either updates both:

```tsx
import { useState } from "react";

function Order() {
  const [count, setCount] = useState(1);

  return (
    <>
      <Counter value={count} onChange={setCount} />
      <Counter value={count} onChange={setCount} />
      <button onClick={() => setCount(1)}>Reset order quantity</button>
    </>
  );
}
```

Without `value`, `defaultValue` initializes internal state; a defined `value` makes it caller-controlled. Passing `value` without handling `onChange` prevents interaction from changing the controlled UI. Parent-driven resets of `count` do not trigger either counter's `onChange`.

## Scenario 2: Accepting, adjusting, or rejecting requests

A cart quantity cannot exceed stock. Keep that rule in the parent storing state:

```tsx
function CartQuantity() {
  const [quantity, setQuantity] = useState(1);
  const stock = 3;

  return (
    <Counter
      value={quantity}
      onChange={(requested) => {
        setQuantity(Math.min(requested, stock));
      }}
    />
  );
}
```

At quantity `3`, another click sends `4` to `onChange`; the parent returns `3`, keeping the UI at `3`. The next click requests `4` again, rather than silently accumulating to `5`.

Parents can also reject requests, for example by not writing state while a form is locked:

```tsx
<Counter
  value={quantity}
  onChange={(requested) => {
    if (locked) return;
    setQuantity(requested);
  }}
/>
```

This is why **`onChange` means “a new value was requested,” not “the new value took effect.”** Notification is synchronous; React commits and parental acceptance are separate events.

### Why consecutive requests accumulate

The hook distinguishes:

- **Current value**: returned to the component for rendering, determined by the caller when controlled or internal state when uncontrolled.
- **Request calculation base**: the latest request result, matching current value without new requests. It resolves subsequent updaters and detects repeated requests without overriding controlled rendering.

The setter supports direct values and functional updaters. Within one event handler, no commit occurs between these calls, so the second updater reads the first request's result:

```tsx
// With current value 1, requests 2 and then 3.
setCurrent((previous) => previous + 1);
setCurrent((previous) => previous + 1);
```

Further calculation depends on the state owner:

- **Controlled**: the next commit realigns the base with the caller's value. The caller may accept, adjust, or reject; the hook schedules a commit even if the caller does not update, ensuring realignment. If current value remains `1`, the next `+1` requests `2` again.
- **Uncontrolled**: requests write internal state. Unrelated renders or earlier update commits do not overwrite a pending request calculation base.

### Confirmation and asynchronous validation

Store pending requests separately from confirmed values when confirmation is required:

```tsx
function ConfirmedQuantity() {
  const [quantity, setQuantity] = useState(1);
  const [pending, setPending] = useState<number>();

  return (
    <>
      <Counter value={quantity} onChange={setPending} />
      <p>Pending: {pending ?? "No request"}</p>
      <button
        disabled={pending === undefined}
        onClick={() => {
          if (pending === undefined) return;
          setQuantity(pending);
          setPending(undefined);
        }}
      >
        Confirm quantity
      </button>
    </>
  );
}
```

Starting at `1`, two separate clicks each commit against `1`, so the pending value is `2`, not `3` accumulated across commits. Only two consecutive updater calls within one event request `2` and `3`.

Asynchronous validation follows the same rule: display old `value` while waiting, then let the parent write the accepted value. The hook does not store async drafts or resolve out-of-order responses. For immediate display, update a parent-owned draft first, store validation results separately, and handle stale responses in the request layer.

## Scenario 3: Updating multiple date fields consecutively

A year/month picker may change year and then month in one interaction. Spreading the currently rendered `date` in both updates restores the old year on the second request:

```tsx
// Assume date is { year: 2026, month: 7 }.
setDate({ ...date, year: 2030 });
setDate({ ...date, month: 8 });
// The second request is { year: 2026, month: 8 }, overwriting the requested year.
```

Derive each update from the preceding request through an updater to retain both changes. Consecutive requests follow this rule in both controlled and uncontrolled modes:

```tsx
type YearMonth = { year: number; month: number };

function MonthShortcut() {
  const [date, setDate] = useControllableValue<YearMonth>({
    defaultValue: { year: 2026, month: 7 },
    onChange: (next) => console.log(next),
  });

  function jump() {
    setDate((previous) => ({ ...previous, year: 2030 }));
    setDate((previous) => ({ ...previous, month: 8 }));
  }

  return <button onClick={jump}>{date.year}-{date.month}</button>;
}
```

One click sends `{ year: 2030, month: 7 }` then `{ year: 2030, month: 8 }` to `onChange`; uncontrolled rendering ends at `2030-8`. Controlled usage preserves request order, but the parent still determines the final display.

For one notification, combine changes into `setDate((previous) => ({ ...previous, year: 2030, month: 8 }))`. The hook composes calculations but does not merge distinct requested values into one callback.

## Scenario 4: Repeated and reverted requests

Dragging, keyboard, and clicks may request the same value. The hook compares the **previous request result** with the new result using `Object.is`, skipping internal updates and `onChange` when equal.

Each row independently starts from current value `1` within one event handler:

| Setter calls | `onChange` history | Reason |
| --- | --- | --- |
| `setCurrent(1)` | None | Value unchanged |
| `setCurrent(2); setCurrent(2)` | `2` | Second request matches the previous one |
| `setCurrent(2); setCurrent(1)` | `2 → 1` | Returning to the original value is a valid request reversing the preceding request |
| Two `setCurrent(current + 1)` calls | `2` | Both use rendered `current`, requesting the same value |
| Two `setCurrent(p => p + 1)` calls | `2 → 3` | Second reads the preceding request result |

This is not permanent deduplication across interactions. If a controlled parent rejects `2` and commits `1`, requesting `2` again notifies again. Initialization, external prop changes, and React render replays do not add `onChange` calls.

Objects and arrays are compared by reference, not contents. Create a new object for changes; return the original reference to skip notification when the application value is unchanged:

```tsx
setDate((previous) =>
  previous.month === 8 ? previous : { ...previous, month: 8 },
);
```

## Scenario 5: Clearable fields and asynchronous initial values

Date or rating fields often use `undefined` for “unselected.” Default control detection uses `value !== undefined`, so explicitly set `controlled: true` from the first render for these fields:

```tsx
function OptionalScore({
  value,
  onChange,
}: {
  value: number | undefined;
  onChange: (next: number | undefined) => void;
}) {
  const [score, setScore] = useControllableValue<number | undefined>({
    controlled: true,
    value,
    onChange,
  });

  return (
    <div>
      <span>Rating: {score ?? "Unselected"}</span>
      <button onClick={() => setScore(5)}>Choose 5 stars</button>
      <button onClick={() => setScore(undefined)}>Clear</button>
    </div>
  );
}

function Review() {
  const [score, setScore] = useState<number>();
  return <OptionalScore value={score} onChange={setScore} />;
}
```

It starts as “Unselected,” displays `5` after selection, and returns to “Unselected” after clearing, remaining controlled throughout. Even with `defaultValue: 3`, an explicitly controlled empty value is not replaced by `3`. Including `undefined` in the value type permits clearing; `controlled: true` determines runtime ownership.

For data loaded asynchronously before passing `value`, decide ownership up front. Use `controlled: true` from the first frame for parent ownership. To use fetched data only as an uncontrolled initial value, wait until it is ready before mounting.

## Scenario 6: Switching records and resetting defaults

`defaultValue` initializes the first mount. If `<Counter defaultValue={1} />` has been incremented to `2`, changing `defaultValue` to `10` leaves it at `2`, preserving user edits.

Choose a reset strategy when editing different records:

```tsx
// Remount when changing records to use the new record's initial quantity.
<Counter key={record.id} defaultValue={record.quantity} />
```

```tsx
// Use controlled values when a form needs resets or prefilling at any time.
<>
  <Counter value={quantity} onChange={setQuantity} />
  <button onClick={() => setQuantity(record.quantity)}>Restore record quantity</button>
</>
```

With an unchanged `key`, new `defaultValue` does not reset state. Changing `key` recreates local state for the component and subtree, appropriate for switching whole records. Controlled values are more direct for resetting individual fields.

### Keep ownership stable while mounted

Control mode is chosen only on the first render:

```ts
const isControlled = controlled ?? value !== undefined;
```

Switching controlled/uncontrolled mode later warns in the console but does not change the chosen mode. If a controlled value may become `undefined`, consistently pass `controlled: true` from the first render. To actually change modes, remount the hook's component with a different `key`.

An initially `undefined` value followed by asynchronous data does not automatically take over internal state. Keep `controlled` consistent for each mount.

| Initial configuration | Later change | Actual behavior |
| --- | --- | --- |
| `defaultValue: 1`, no `value` | Pass `value: 10` | Warns; keeps internal state |
| `value: 1, defaultValue: 0`, implicit mode | `value` becomes `undefined` | Warns; stays controlled and falls back to initial default `0` |
| `controlled: true, value: undefined` | `value` becomes `10` or clears again | Always controlled, displaying the supplied value |
| `controlled: false, defaultValue: 1` | Supply or change `value` | Always uses internal state and ignores `value` |

## Scenario 7: Saving the setter for later

Timers or subscriptions may retain an earlier setter. Its identity remains stable for one mount and it uses the latest **committed** `onChange`; the controlled calculation base also aligns with the latest committed value.

```tsx
const [current, setCurrent] = useControllableValue({ value, onChange });

function incrementLater() {
  window.setTimeout(() => {
    setCurrent((previous) => previous + 1);
  }, 1_000);
}
```

Assume `value` is a number. If it is `1` on click but the parent commits `10` before the timer fires, the delayed updater requests `11`. Using `setCurrent(current + 1)` instead captures `1` from the click closure and requests `2`. A stable setter does not refresh variables in caller closures.

Calling the setter in a child's layout effect follows the same rule. Call setters in event handlers or effects, never during render. Updaters should be pure; function-valued application data cannot be passed directly as an ordinary value.

The hook guarantees request calculations in call order, not identical cross-priority scheduling or intermediate renders to native `useState`.

## Scenario 8: Passing interaction sources to parents

A control may be operated by keyboard or pointer. Declare an additional argument tuple through the second generic parameter to pass this information with the value, without external temporary variables:

```tsx
type ChangeDetails = { source: "pointer" | "keyboard" };

const [value, setValue] = useControllableValue<
  number,
  [details: ChangeDetails]
>({
  defaultValue: 0,
  onChange(next, details) {
    console.log(next, details.source);
  },
});

// Call inside a keyboard event handler:
setValue((previous) => previous + 1, { source: "keyboard" });
// Callback receives 1 and { source: "keyboard" }, not the updater function.
```

The setter and `onChange` share the same argument tuple. An unchanged requested value does not notify again even if extra arguments differ; log every interaction in its event handler when needed.

## Defaults and type inference

With default control detection, if `value` may be `undefined` or is omitted, a defined default removes `undefined` from the return value, writable value, and updater `previous` types. Explicit `controlled: false` with a defined default follows the same rule:

```tsx
const [date, setDate] = useControllableValue({
  value, // Date | undefined
  defaultValue: new Date(),
  onChange,
});

date.getTime(); // date: Date
setDate((previous) => new Date(previous.getTime() + 1_000));
// previous: Date
```

To keep types consistent with runtime, if an implicitly controlled value later disappears, the hook warns and falls back to the **initial** `defaultValue` while remaining controlled. This guards invalid input rather than switching modes, and ignores later defaults. `null` is not considered missing.

Explicit `controlled: true` respects the application meaning of `undefined`. Even with a default, `value: Date | undefined` keeps return value and updater arguments as `Date | undefined`.

When controlled `value` excludes `undefined`, only the current return value narrows; the setter retains declared `Value`. You can therefore allow clearing even with a currently defined value, and subsequent updater `previous` must account for that clear request:

```tsx
const [date, setDate] = useControllableValue<Date | undefined>({
  controlled: true,
  value: new Date(),
  onChange,
});

date.getTime(); // date: Date
setDate(undefined); // Requests clearing without directly changing controlled rendering.
setDate((previous) => previous ?? new Date()); // previous: Date | undefined
```

Without a default, the initial readable value may be `undefined`, but this does not automatically permit writing `undefined`. For example, `useControllableValue<number>({})` returns `number | undefined`, while its setter accepts only `number` or an updater returning `number`. Explicitly include `undefined` in the value type to allow clearing. Default-value overloads still prohibit writing `undefined` to preserve non-empty guarantees.

## API

### `ControlOptions<Value, Args>`

| Option | Type | Description |
| --- | --- | --- |
| `controlled` | `boolean` | Overrides detection based on `value === undefined`; mode remains fixed on first render |
| `value` | `Value` | Controlled value |
| `defaultValue` | `Value` | Uncontrolled initial value, also the initial fallback when an implicitly controlled value unexpectedly disappears |
| `onChange` | `(value: Value, ...args: Args) => void` | Synchronously receives concrete values from valid update requests and the setter's extra arguments |

### Return value

`useControllableValue` returns `[value, setValue]`:

- `value` is controlled value or internal state; its type includes `undefined` without a defined controlled value or default.
- `setValue(updater, ...args)` accepts a value or functional updater. The defined-controlled-value overload narrows only the return value, retaining declared `Value` for writable values and updater `previous`. Default-value overloads exclude `undefined` from all three. Other cases retain `Value` for writes and include `undefined` in the return value and `previous`.

Related exported types include `ControlOptions<Value, Args>`, `ChangeHandler<Value, Args>`, and `SetValue<Value, Args, Previous = Value>`. In `SetValue`, `Value` describes allowed writes, `Previous` describes what updaters may read, and `Args` describes additional arguments.
