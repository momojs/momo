`useStoragefy` adapts synchronous [Storagefy](/docs/host/guide) entries to React. Storage is the sole data source: the hook returns the stored value or `null` and updates on change notifications.

## Playground

The two subscribers use separate `Storagefy` instances sharing one memory store and key. Operating either updates both. Switch keys to observe independent stored values.

<UseStoragefyPlayground />

| Action | Result |
| --- | --- |
| Initial state or deleted record | Stored value is `null`; the UI shows the configured fallback |
| +1 twice consecutively | Each update reads the latest value; the default display fallback `10` becomes `12` |
| Switch to another key and back | Keys remain independent and the original value is retained |
| Write with expiry `3`, wait 3 seconds, then reread the snapshot | The next read discovers expiry and returns `null`; no automatic expiry notification |

The demo creates independent `MemoryStorage` per mount and resets on reload. Browser persistence and cross-document synchronization are covered below.

## Reading and updating

Declare storage instances outside components or create them by logical key with `useMemo`. Creating an instance every render causes unnecessary resubscriptions.

```tsx
import { Storagefy } from "@momots/host/storage";
import { useStoragefy } from "@momots/design/hooks";

const counter = new Storagefy<number>("counter");

function Counter() {
  const [storedCount, setStoredCount] = useStoragefy(counter);
  const count = storedCount ?? 10;

  return (
    <div>
      <output>{count}</output>
      <button
        type="button"
        onClick={() => setStoredCount((previous) => (previous ?? 10) + 1)}
      >
        Increment
      </button>
      <button type="button" onClick={() => setStoredCount(null)}>
        Delete record
      </button>
    </div>
  );
}
```

You can also import directly from `@momots/design/hooks/use-storagefy`.

Here `10` is a display fallback; the hook does not write it automatically. Deletion returns `null`, and `?? 10` displays `10` again. `0`, `false`, and empty strings are valid values; do not use `value || fallback` for missing-value detection.

| Operation | Behavior |
| --- | --- |
| Read a missing entry | Returns `null` |
| `setValue(value)` | Synchronously writes and notifies subscribers |
| `setValue(previous => next)` | Calculates from the latest stored value at write time; `previous` is `T \| null` |
| `setValue(null)` or updater returns `null` | Deletes the entry; subscribers read `null` |
| Consecutive updates | Each reads the preceding written result |
| Reads/writes denied or a write fails | Errors propagate without silently switching storage |

Call the setter from ordinary callbacks such as click handlers. Its reference remains stable while the storage instance and `expires` references are unchanged; changed arguments produce a setter bound to the new arguments.

Functional updates are synchronous read-then-write operations, not atomic transactions across browser tabs. Values must follow underlying JSON serialization rules; functions cannot be persisted.

## Synchronization scope

`Storagefy` instances sharing the **same underlying storage instance and key** receive the same changes. Identical keys in `localStorage`, `sessionStorage`, or different `MemoryStorage` instances are independent.

- In the current page, `Storagefy.set()`, `remove()`, `expire()`, and `Storagefy.clear()` synchronously notify subscribers, including memory storage.
- Native browser `storage` events receive changes from other documents, filtered by `storageArea` and key. Native `clear()` events with `key === null` also reread the current entry.
- Native `localStorage` events reach other same-origin documents sharing storage; `sessionStorage` propagation depends on browser session and top-level browsing context.
- Calling native `setItem()`, `removeItem()`, or `clear()` directly in the current page does not notify that page. Modify through `Storagefy` or explicitly call `Storagefy.dispatch(key, newValue, oldValue, storageArea)` afterward.

Do not write storage during render. Subscriptions reflect completed storage changes; they do not hold pending React application state.

## Switching entries

```tsx
import { useMemo } from "react";
import { Storagefy } from "@momots/host/storage";
import { useStoragefy } from "@momots/design/hooks";

function Draft({ documentId }: { documentId: string }) {
  const cell = useMemo(
    () => new Storagefy<string>(`draft:${documentId}`),
    [documentId],
  );
  const [draft, setDraft] = useStoragefy(cell);

  return (
    <textarea
      aria-label="Draft"
      value={draft ?? ""}
      onChange={(event) => setDraft(event.target.value)}
    />
  );
}
```

A new instance's snapshot is read during the current render and its subscription replaces the old one at commit. Unmounting unsubscribes. With a `() => Storage` resolver, keep underlying storage stable during an instance's subscription; create a new `Storagefy` when changing storage areas.

## Object snapshots and expiry

Unchanged raw storage retains the same object snapshot reference, avoiding repeated JSON decoding and rerender loops. Treat snapshots as read-only; return new objects through the setter when updating.

```tsx
const [value, setValue] = useStoragefy(counter, {
  expires: 300,
});

// Each write resets expiry to 300 seconds after that write.
const increment = () => setValue((previous) => (previous ?? 0) + 1);
```

`expires` is in seconds and may be a function evaluated on each write. Omitted or `0` means no expiry; negatives make the value expired on its next read. Changing the hook's `expires` does not modify existing entries; use `cell.expire(seconds)` to change their deadline.

The hook has **no expiry timer**: expiration alone does not rerender; the next snapshot read returns `null`. Renders and storage notifications recheck expiry. Snapshot reads do not delete expired or damaged entries. `Storagefy.get()` retains read-time cleanup, and setters call it before updates.

## SSR and hydration

Server rendering and initial client hydration use an empty `MemoryStorage` isolated per hook mount, returning `null`. During this period, the supplied instance's browser-storage resolver is not evaluated and `localStorage` is not accessed.

After hydration, the hook reads the supplied instance's actual value and subscribes. Client-only mounts read actual values directly. Memory snapshots are never written back to the browser, never overwrite saved data, and are not shared across server requests.

Prefilled server data in the supplied instance is not used as the hydration initial value. Pass server application data separately through page props or another mechanism.

## API

```ts
interface UseStoragefyOptions {
  expires?: number | (() => number);
}

type StoragefyUpdater<T> =
  | T
  | null
  | ((previous: T | null) => T | null);

type StoragefySetter<T> = (value: StoragefyUpdater<T>) => void;

function useStoragefy<T>(
  storage: Storagefy<T>,
  options?: UseStoragefyOptions,
): readonly [T | null, StoragefySetter<T>];
```

Only synchronous `Storagefy` is accepted, not `StoragefyAsync`.
