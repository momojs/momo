`usePresenceGate` keeps a parent mounted after closing is requested until registered child `AnimatePresence` boundaries finish exiting, then allows the parent to exit. It suits overlays, menus, and collapsible regions that must exit inside-out.

## Why use it

Consider an overlay containing a backdrop and content. Both must finish exiting before their Portal disappears. Using `open && <Portal />` for the whole structure removes the child animation hosts as soon as `open` becomes `false`.

A fixed `setTimeout` delay is difficult to maintain: changes to child durations or reopening mid-exit mean elapsed time no longer represents actual completion.

The hook separates `open`, the application's desired state, from `visible`, whether the parent must remain mounted. Children report exit completion through gates, and the parent waits for all participants.

| Problem | Hook behavior |
| --- | --- |
| Immediate parent unmount truncates child exits | Temporarily retains the parent until children can finish |
| Backdrop and content have different durations | Registers separate gates and releases after all complete |
| A completed child rerenders due to other state | Completed gates do not rejoin waiting during the same close cycle |
| User reopens during exit | Keeps `visible` true, clears current waits, and reenters content |
| An optional subtree disappears while closing | Removes its wait so the parent cannot remain stuck |
| No children need waiting | Releases the parent directly in the closing effect |

Use `AnimatePresence` directly for a single exit layer. Use `usePresenceGate` to coordinate independent nested exit boundaries or enforce inner-before-outer completion. It does not define animations, manage focus, or change application open state.

`visible = false` means the hook no longer retains the parent. An outer `AnimatePresence` can still retain its exiting DOM until its own animation completes. The demo therefore distinguishes “parent exiting” from “parent unmounted.”

## Scenario 1: Inner content exits before its container

The inner layer uses `open` to decide when to exit; the outer layer uses `visible` to decide when to release. Separating these conditions establishes inside-out order:

```tsx
import { AnimatePresence, motion, useReducedMotion } from "motion/react";

import { usePresenceGate } from "@momots/design/hooks";

function NestedPanel({ open }: { open: boolean }) {
  const { visible, createGate } = usePresenceGate(open);
  const reduced = useReducedMotion();

  return (
    <AnimatePresence initial={false}>
      {visible && (
        <motion.section
          key="panel"
          initial={{ opacity: 0 }}
          animate={{ opacity: 1 }}
          exit={{ opacity: 0 }}
          transition={{ duration: reduced ? 0 : 0.2 }}
        >
          <AnimatePresence
            initial={false}
            onExitComplete={createGate("content")}
          >
            {open && (
              <motion.div
                key="content"
                initial={{ opacity: 0 }}
                animate={{ opacity: 1 }}
                exit={{ opacity: 0 }}
                transition={{ duration: reduced ? 0 : 0.4 }}
              >
                Panel content
              </motion.div>
            )}
          </AnimatePresence>
        </motion.section>
      )}
    </AnimatePresence>
  );
}
```

The original `open` controls children while `visible` controls the parent container. Closing follows this order:

1. `open` becomes `false`; `visible` temporarily stays `true`.
2. The closing render calls `createGate("content")` to register the child's exit task.
3. Child `AnimatePresence` finishes exiting and calls the returned handler.
4. Once all gates complete, `visible` becomes `false` and the parent begins its own exit.

Here content exits over roughly `0.4` seconds, then the parent fades out over roughly `0.2` seconds. Release depends on completion callbacks, not these durations, with no extra countdown.

### Keep the waiting component mounted

The caller should continuously render this component and change only `open`:

```tsx
// Correct: the component can observe the true-to-false transition.
<NestedPanel open={open} />
```

The following removes the hook's component immediately, leaving no opportunity to wait:

```tsx
// Incompatible with this waiting logic: closing immediately unmounts the entire component.
{open && <NestedPanel open={open} />}
```

Child `AnimatePresence` itself must also remain in the tree; toggle only its managed animated content. Do not wrap the entire `AnimatePresence` in `open`.

## Scenario 2: Parallel backdrop and content exits

One parent can register multiple gates. Here the backdrop exits faster than content; both start together and the parent releases only after both finish:

```tsx
function OverlayLayers({ open }: { open: boolean }) {
  const { visible, createGate } = usePresenceGate(open);
  const reduced = useReducedMotion();

  return (
    <AnimatePresence initial={false}>
      {visible && (
        <motion.div
          key="root"
          exit={{ opacity: 0 }}
          transition={{ duration: reduced ? 0 : 0.2 }}
        >
          <AnimatePresence onExitComplete={createGate("backdrop")}>
            {open && (
              <motion.div
                key="backdrop"
                className="bg-black/20"
                exit={{ opacity: 0 }}
                transition={{ duration: reduced ? 0 : 0.2 }}
              >
                Backdrop illustration
              </motion.div>
            )}
          </AnimatePresence>
          <AnimatePresence onExitComplete={createGate("content")}>
            {open && (
              <motion.div
                key="content"
                exit={{ opacity: 0 }}
                transition={{ duration: reduced ? 0 : 0.5 }}
              >
                Content illustration
              </motion.div>
            )}
          </AnimatePresence>
        </motion.div>
      )}
    </AnimatePresence>
  );
}
```

This waits for all sibling tasks; **it does not sequence the two children**. Normal child waiting takes roughly `max(0.2, 0.5)` seconds rather than their sum, followed by the parent exit.

Each gate represents one `AnimatePresence` completion signal. If that boundary contains multiple directly exiting children, its `onExitComplete` already means all have completed; no gate per DOM node is needed.

This example demonstrates only exit coordination. Use [Dialog](/docs/design/dialog), already integrated with the hook, for actual dialogs. [Accordion](/docs/design/accordion) also uses `visible` to retain exiting panels.

## Scenario 3: Reopening during closing

Users need not wait for animation completion to reverse closing:

```tsx
import { useState } from "react";

function PanelExample() {
  const [open, setOpen] = useState(true);

  return (
    <>
      <button onClick={() => setOpen((previous) => !previous)}>
        {open ? "Close" : "Reopen"}
      </button>
      <NestedPanel open={open} />
    </>
  );
}
```

| Moment | `open` | `visible` | Behavior |
| --- | --- | --- | --- |
| Open | `true` | `true` | Content displays normally |
| Closing requested, children still exiting | `false` | `true` | Parent retained while waiting |
| Reopened now | `true` | `true` | Current waiting clears and content reenters |
| Closed again later | `false` | `true` | Registers a new close cycle until all children finish |

Keep root and logical child keys stable so Motion handles reentry of the same elements. Changing the entire component's key on every toggle to “restart animation” loses retained state.

Completion notifications cannot close an already reopened parent. The hook manages opening and waiting relationships; Motion configuration determines reversal, translation, and scaling behavior.

## Scenario 4: Optional subtrees disappear during closing

Overlays may have optional help, and menus may dynamically remove areas. Give dynamic targets stable unique application keys, and call `createGate` alongside its corresponding `AnimatePresence`:

```tsx
// Place inside the parent retained by visible.
{showHelp && (
  <AnimatePresence onExitComplete={createGate("help")}>
    {open && (
      <motion.aside key="help" exit={{ opacity: 0 }}>
        Help content
      </motion.aside>
    )}
  </AnimatePresence>
)}
```

If help exists when closing starts, its exit is awaited. If `showHelp` becomes false mid-close, its entire subtree and gate disappear from the current render; the hook removes that wait and releases once remaining gates complete. Ordinary rerenders do not re-enlist completed gates.

Removing the entire subtree abandons its remaining exit animation. To play the complete help exit, retain its `AnimatePresence` and let only the inner `motion.aside` exit based on `open`.

Do not add a new empty gate during closing for content that was never shown: without an exiting element, a completion callback may never arrive. Wait only for regions actually exiting this cycle and able to report completion.

### Keys identify waiting regions

The key in `createGate("help")` identifies the wait to the hook; `<motion.aside key="help">` identifies the element to React and Motion. These are distinct roles and may share a name for readability, but both must remain stable.

Concurrent regions must not share gate keys, or either completion could count as the same wait. Use record IDs for dynamic lists, not array indices or newly created `Symbol()` values on every render.

Without a key, `createGate()` identifies gates by call order in the current render. Use this only for fixed counts and order; always provide explicit keys for branches and dynamic lists.

## Scenario 5: No children need waiting

If no `createGate` is called, changing `open` from true to false releases retained state in an effect instead of waiting for a nonexistent completion event.

```tsx
function SimpleShell({ open }: { open: boolean }) {
  const { visible } = usePresenceGate(open);

  return (
    <AnimatePresence>
      {visible && (
        <motion.div key="shell" exit={{ opacity: 0 }}>
          Ordinary content exits with its parent
        </motion.div>
      )}
    </AnimatePresence>
  );
}
```

For this single layer, using `open` directly is usually sufficient. This scenario illustrates when all optional children are absent: the hook stops waiting, while outer Motion still completes the parent's exit.

## Scenario 6: Reduced motion still uses completion signals

With reduced-motion preferences, shorten or remove spatial animation without changing gate connections:

```tsx
const reduced = useReducedMotion();

<AnimatePresence onExitComplete={createGate("content")}>
  {open && (
    <motion.div
      key="content"
      exit={{ opacity: 0 }}
      transition={{ duration: reduced ? 0 : 0.3 }}
    >
      Panel content
    </motion.div>
  )}
</AnimatePresence>
```

At duration `0`, `AnimatePresence` still reports completion and releases the parent. Do not replace callbacks with timers or skip them because animation is faster. “Complete animation immediately” in the demo exercises this path.

## Scenario 7: Logging exits while completing gates

To add application logic in `onExitComplete`, obtain the gate handler during render and invoke it in the completion callback:

```tsx
// Run in the corresponding AnimatePresence render path.
const finishContent = createGate("content");

<AnimatePresence
  onExitComplete={() => {
    finishContent();
    console.log("Content exit complete");
  }}
>
  {open && <motion.div key="content" exit={{ opacity: 0 }} />}
</AnimatePresence>
```

Do not write `onExitComplete={() => createGate("content")}`: it registers only after exiting and never invokes the returned handler. Logging without calling `finishContent()` also leaves the parent waiting.

A child callback means only that child has completed. To know the parent has also exited, observe the **outermost** `AnimatePresence.onExitComplete` wrapping it; `visible = false` does not mean every DOM node has been removed.

## Troubleshooting

| Symptom | Cause and solution |
| --- | --- |
| Children disappear immediately on close | Check whether the caller unmounts the hook's component or removes the entire child `AnimatePresence` using `open` |
| Stuck at `open = false, visible = true` | Children must use `open`. Using `visible` creates circular waiting: the parent waits for child completion while the child waits for parent release before exiting |
| Parent disappears after only one region exits | Check missing gates or shared keys between regions |
| Parent remains visible after closing | Distinguish waiting for children from the parent's own exit phase; `visible` does not indicate DOM removal |
| Logging works but parent never releases | Ensure the completion callback invokes the handler created during render, rather than merely registering or logging |
| No visible exit after `hidden` / `display: none` | CSS hiding may take effect before Motion exit; retain the animation host until the appropriate phase before hiding or unmounting |

Call `createGate` during the current render of the component owning the hook, not later in an event, effect, or exit callback. It does not wait for network requests, route changes, or data saves; handle those within their application workflows.

## API

```ts
function usePresenceGate(open: boolean): {
  visible: boolean;
  createGate: (key?: string | number | symbol) => () => void;
};
```

| Return value | Description |
| --- | --- |
| `visible` | Immediately true when open; after closing, retained until every current gate completes or is removed. Initially false when `open = false` |
| `createGate(key?)` | Registers a child during render and returns its `onExitComplete` handler; explicit keys may be `string`, `number`, or `symbol` |

`open: boolean` should reflect current effective application state. If a controlled parent rejects closing, continue passing true and the hook will not release. Gate handlers take no arguments and return no Promise.

Related exported types include `PresenceGateKey`, `PresenceGateExitHandler`, and `UsePresenceGateResult`.
