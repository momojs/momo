This page precisely defines Drive's public API. If you are deciding which entry point to use, start with
[Getting started](/docs/drive); to build a client through an example, read the [tutorial](/docs/drive/tutorial).

Relative URLs in snippets assume a same-origin browser environment. Drive has no `baseURL`; the current Fetch runtime determines
whether a target can be sent. Bun/Node.js generally require absolute URLs. Undefined domain types and functions represent
application dependencies.

## Public entry points

The root entry includes classes, functions, and types needed for everyday usage:

```ts
import {
  Drive,
  DriveContext,
  isRawTextBody,
  parser,
  repeat,
  toSearchParams,
} from "@momots/drive";
```

The package also provides these subpaths for importing specific capabilities. They are not separate APIs.

| Entry | Contents |
| --- | --- |
| `@momots/drive` | Everyday request APIs; optional recipes have dedicated subpaths |
| `@momots/drive/core` | `Drive` |
| `@momots/drive/context` | `DriveContext` |
| `@momots/drive/parser` | Default parser, `isRawTextBody`, and related types |
| `@momots/drive/recipes/csrf` | `csrf`, `CsrfTokenMissingError`, and `CsrfOptions`; see [Recipes](/docs/drive/recipes#csrf) |
| `@momots/drive/stages` | Optional stages, currently including `repeat` |
| `@momots/drive/stages/repeat` | `repeat` |
| `@momots/drive/types` | Type definitions, including some low-level helpers |

## Choosing a request entry point

| Entry | HTTP method | Arguments | Return | `receiver` |
| --- | --- | --- | --- | --- |
| HTTP shortcuts | Fixed by method name | Object or positional | Parsed `T` | Not allowed |
| `exec()` | Explicit or inferred | Object | Parsed `T` | Not allowed |
| `request()` | Explicit or inferred | Object | `DriveFetchedContext<T>` | Allowed |

The seven shortcuts are `get`, `put`, `post`, `head`, `patch`, `delete`, and `options`.
Drive has no `trace` or `connect` shortcut; passing methods through `exec()` still obeys the current Fetch
runtime's method restrictions.

## `Drive`

### Constructor

```ts
declare class Drive {
  constructor(options?: DriveConstructorParams);
}

type DriveConstructorParams = DriveParams | DriveMiddlewareEntry[];
```

`options` may be a complete configuration object or a middleware-entry array:

```ts
const drive = new Drive({
  middlewares: [["/api/**", authMiddleware]],
});

const compact = new Drive([
  ["/api/**", authMiddleware],
]);
```

The constructor copies the supplied `middlewares` array; modifying the original array after construction does not change registered
middleware.

`DriveParams`:

| Field | Type | Purpose |
| --- | --- | --- |
| `middlewares` | `DriveMiddlewareEntry[]` | Pre-register middleware |
| `stamp` | `() => string` | Generate `req.id` |
| `parser` | `<T>() => DriveBodyParse<T>` | Create the default response parser |
| `stringifier` | `() => DriveDataStringify` | Create the JSON serializer |
| `stages.prepare` | `DriveStagePrepare` | Replace request preparation |
| `stages.send` | `DriveStageSend` | Replace transport |
| `stages.receive` | `DriveStageReceive` | Replace response reception |

Instance settings are defaults. A request-level `parser`, `stringifier`, or `stages.*` takes
precedence.

### `use()`

```ts
declare class Drive {
  use(pattern: DrivePattern, middleware: DriveMiddleware): this;
}
```

Register instance middleware and return the current instance for chaining. See
[Middleware and matching](#middleware-and-matching) for matching and ordering.

### HTTP shortcuts

All shortcuts share two supported overloads:

```ts
interface DriveMethod {
  <T>(options: DriveMethodOptions<T>): Promise<T>;
  <T>(api: string, data?: object, init?: DriveMethodInit<T>): Promise<T>;
}
```

```ts
await drive.post<User>({
  api: "/api/users",
  json: { name: "Ada" },
});

await drive.post<User>("/api/users", { name: "Ada" }, {
  timeout: 5_000,
});
```

Object and positional forms have equal capabilities and support. Object form directly accepts `query`, `json`, `body`,
or `data`; the second positional argument maps to the same `data` field and the third contains other initialization options.

A shortcut's method is fixed by its name and cannot be overridden with `method`. The return generic `T` is a caller assertion; the parsed result may still be
`undefined` at runtime. Declare `void` for known empty responses and optional responses as
`T | undefined`.

### `exec()`

```ts
declare class Drive {
  exec<T>(options: DriveOpts<T> & { receiver?: never }): Promise<T>;
}
```

`exec()` accepts object arguments for Fetch methods without a shortcut, or requests that infer the method automatically while
returning only the body.

```ts
const report = await drive.exec<Report>({
  api: "/api/reports/current",
  method: "REPORT",
});
```

`exec()` cannot bypass Fetch restrictions on methods such as `TRACE` and `CONNECT`, and does not accept `receiver`.

### `request()`

```ts
declare class Drive {
  request<T>(options: DriveOpts<T>): Promise<DriveFetchedContext<T>>;
}
```

Returns the full Context for response status, headers, the raw `Response`, or streams. It is the only request entry point that accepts
`receiver`.

```ts
const context = await drive.request<User>({
  api: "/api/users/u1",
  method: "GET",
});

context.res.raw;     // Response
context.res.status;  // number
context.res.headers; // Headers
context.res.body;    // User | undefined
```

Successful `request()` calls always provide `raw`, `status`, and `headers`. The presence of `body` and `stream`
depends on response content and the parser. `raw` is the same Response passed to the parser, not a repeatedly readable
clone; ordinary parsing usually consumes its body, while receiver mode transfers body consumption to the proxy stream.

## Request parameters

Here, query means URL query parameters, body means the request body, and fragment means the URL portion after `#`.

### Base shape

```ts
type DriveOpts<T> = DriveInit<T> & {
  api: string;
  data?: object;
};
```

Alongside the Drive fields below, `DriveInit<T>` accepts standard `RequestInit` properties such as `method`,
`headers`, `signal`, `credentials`, and `cache`. Drive redefines `body` using its mutually exclusive request-body
types.

| Field | Type | Description |
| --- | --- | --- |
| `api` | `string` | Target passed to the current Fetch runtime; Drive adds no base URL |
| `query` | `URLSearchParams` | Explicit query channel |
| `json` | `unknown` | Explicit JSON body channel; mutually exclusive with `body` |
| `body` | `BodyInit \| null` | Explicit Fetch body channel; mutually exclusive with `json` |
| `data` | `object` | Automatic channel; see below |
| `timeout` | `number` | Default prepare merges timeout cancellation into `req.signal` after encoding; milliseconds |
| `middlewares` | `DriveMiddleware<T>[]` | Middleware for this request only |
| `parser` | `() => DriveBodyParse<T>` | Per-request parser factory |
| `receiver` | `DriveReceiver<T>` | Per-request stream-progress callback; `request()` only |
| `stringifier` | `() => DriveDataStringify` | Per-request stringifier factory |
| `stages` | `{ prepare?; send?; receive? }` | Per-request stage overrides |

### Data channels

Explicit channels:

| Field | Behavior |
| --- | --- |
| `query` | Merge into URL before existing query parameters; retain duplicate keys and fragment |
| `json` | Serialize with the current stringifier; default `Content-Type` to `application/json` if absent |
| `body` | Pass through as a Fetch body; Drive does not infer a JSON header |

The fragment remains in `context.api`, but Fetch semantics still prevent it from being sent to the server as part of the HTTP
request target.

Automatic `data` channel:

| `data` value | Behavior |
| --- | --- |
| `URLSearchParams` | Query parameters |
| Plain object or array | JSON body |
| `Blob` / `File`, `FormData`, BufferSource, `ReadableStream` | Native Fetch body |

The public type of `data` is `object`, but only the values above are supported. Other objects such as `Date`, `Map`, and custom
classes produce neither query nor body on their own; combined with `json` or non-`null` `body`,
they still count as duplicate input and are rejected. Do not rely on this invalid usage: convert first or use explicit
`json` / `body`. String bodies must also use `body`. To send `URLSearchParams` as an
`application/x-www-form-urlencoded` body, place it in `body`, not `data`.

Plain objects and arrays in `data` mean a JSON body, not query parameters. Thus
`get(api, { q: 1 })` attempts a GET body and encounters Fetch's GET-body restriction. For GET queries,
use `URLSearchParams` or object-style `query`.

### Channel conflicts

Two rules determine whether a combination is valid:

- At most one query source: `query` or `URLSearchParams data`;
- At most one body source: `json`, non-`null` `body`, or body-shaped `data`.

One query source can coexist with one body source. Duplicate sources reject with `TypeError` before
sending; there is no override order. `body: null` means no explicit body and does not conflict with `data`.

### HTTP methods

- Shortcut methods are fixed by name and cannot be overridden;
- `request()` and `exec()` may specify `method` explicitly;
- Without a method, encoding selects `GET` when no body exists and `POST` otherwise;
- Fetch still enforces restrictions on GET/HEAD bodies and prohibited methods.

Instance middleware matching happens before automatic method inference. Predicates or middleware depending on the method should use shortcuts
or an explicit `method` in `request()` / `exec()`. During matching, explicit methods retain the caller's
casing; normalize in the predicate for case-insensitive matching.

### timeout and signal

With default prepare, a finite nonnegative `timeout` starts a timer after encoding and merges its
cancellation signal into `req.signal`. Negative values, `NaN`, and infinities count as unset; `timeout: 0` still enables it.
When the caller also supplies `signal`, both cancellation sources apply.

This is cooperative cancellation, not a hard deadline forcing Promise rejection. Default send passes the signal
to Fetch; custom send, parser, middleware, or other asynchronous work that ignores it is not interrupted directly by
the timer.

The timer lasts until the internal send/receive chain finishes. With repeat, unless `effect` replaces
`req.signal`, all attempts, effects, and delays share one timer without per-attempt resets;
Fetch and delay observe the signal. Encoding, outer middleware work before and after `next()`, and
stream consumption after `request()` returns are outside the timed lifecycle. To continue cancellation during downloads, use a caller-owned
`AbortSignal`.

## Return model

### Body-only APIs

HTTP shortcuts and `exec()` return only `res.body`. They accept no receiver and do not expose Context,
status, or the raw response.

If the parser has not consumed the raw Response body, Drive requests its cancellation before discarding Context. If a parser
produces a stream, these APIs reject and require `request()` so they do not create a stream the caller cannot
access.

### `DriveFetchedContext<T>`

```ts
type DriveFetchedContext<T> = DriveContext<T> & {
  res: DriveFetchedResponse<T>;
};

type DriveFetchedResponse<T> = {
  raw: Response;
  status: number;
  headers: Headers;
  type?: string;
  charset?: string;
  body?: T;
  stream?: ReadableStream<Uint8Array>;
};
```

| Field | Meaning |
| --- | --- |
| `raw` | Original Fetch `Response` |
| `status` | HTTP status code |
| `headers` | Response headers |
| `type` | Simplified category inferred from Content-Type |
| `charset` | Charset declared in Content-Type |
| `body` | Ordinary parser result |
| `stream` | Caller-consumed stream in receiver mode |

`4xx` and `5xx` do not themselves reject the Promise. Before `request()` returns, network failures, cancellation, encoding
errors, and exceptions from middleware, stages, parsers, or repeat policies still reject it. After
`request()` returns `res.stream`, subsequent network, cancellation, or receiver errors are reported by stream reads
and do not alter the settled request Promise.

## Middleware and matching

### Function signature

```ts
type DriveNext = () => Promise<void>;

type DriveMiddleware<T = unknown> = (
  context: DriveContext<T>,
  next: DriveNext,
) => void | Promise<void>;
```

Code before `await next()` handles requests; code afterward handles responses. Each middleware may call `next()` at most once.

Omitting `next()` short-circuits. Drive still checks `res.raw`, `res.status`, and
`res.headers`; any missing field rejects the Promise, while all three allow success.
Shortcuts and `exec()` then return the current `res.body`, even if `undefined`. Short-circuit logic should therefore
throw explicitly or provide a complete response appropriate to the entry point.

### Match patterns

```ts
type DrivePattern = string | DrivePredicate;
type DrivePredicate = (snapshot: DriveContextSnap) => boolean;
```

String patterns match paths without query parameters or fragments:

| Pattern | Meaning |
| --- | --- |
| `*` | Any path |
| `/api/users` | Literal segments; also matches repeated or trailing `/` |
| `/api/*` | Zero or more characters at one level after `/api/` |
| `/api/**` | `/api` itself and descendants at any depth |
| `/api/u?ers` | `?` matches one non-`/` character |
| `/api/\*` | `\` escapes the next wildcard character |
| `!/api/public/**` | Paths not matching this pattern |

String patterns use segment-glob semantics: `/` matches one or more consecutive separators, and trailing separators
are optional. A request can match several instance middleware entries. Except for `*`, strings enter the onion stack in descending
length after removing `!`; predicates follow these nonempty patterns and precede `*`. Equal priorities retain registration order.
Per-request `middlewares` execute after matched instance middleware, in supplied order.

Drive completes all instance matching before executing middleware. Predicates read a snapshot of the newly created request, so
they cannot see later middleware changes to headers, api, or method. Matching also precedes prepare and automatic method
inference.

## `DriveContext<T>`

Drive creates a Context for every request; manual construction is normally unnecessary.

```ts
declare class DriveContext<T = unknown> {
  constructor(api: string, params?: RequestInit & {
    id?: string;
    data?: object;
    query?: URLSearchParams;
    json?: unknown;
  });
}
```

### Fields

| Field | Type | Meaning |
| --- | --- | --- |
| `api` | `string` | Actual target; may differ from input after query encoding |
| `url` | `URL \| null` | Parsed input api when it is an absolute URL |
| `path` | `string` | Pathname used for matching, without query or fragment |
| `req` | `DriveRequest` | Request ID and standard Fetch initialization state |
| `data` | `object \| undefined` | Automatic input awaiting encoding |
| `query` | `URLSearchParams \| undefined` | Explicit query awaiting encoding |
| `json` | `unknown` | Explicit JSON awaiting encoding |
| `res` | Response state object | raw, status, headers, body, stream, etc. |

`url` and `path` describe the target at Context creation and are used for matching; later query encoding or changes to
`api` do not recompute them. `api` is the sendable target. The request ID is `req.id`, and Context normalizes headers
to `Headers`.

### `encode()`

```ts
declare class DriveContext<T = unknown> {
  encode(options?: { stringify?: DriveDataStringify }): this;
}
```

Encode query and body into a sendable request and infer `req.method` when absent. Throw `TypeError` for
[channel conflicts](#channel-conflicts) or JSON that cannot serialize to a string.

### `decode()`

```ts
declare class DriveContext<T = unknown> {
  decode(response: Response): void;
}
```

Write Response `status`, `headers`, content category, and charset into `res`, without reading its body or
setting `res.raw`.

### `toSnap()`

```ts
declare class DriveContext<T = unknown> {
  toSnap(): DriveContextSnap<T>;
}
```

Return a read snapshot for predicates and repeat decisions. `req.headers`, existing `res.headers`, and
`query` are independent copies; array/plain-object `data/json` and plain-object `res.body`
are cloned. Other platform objects are not deep-cloned; `res.raw` and `res.stream` retain references. Response
bodies still obey single-consumption rules.

## parser, stringifier, and receiver

These options have similar-looking function shapes but different contracts:

| Option | Shape | Invocation |
| --- | --- | --- |
| `parser` | Factory `() => DriveBodyParse<T>` | Obtain a parser for each request |
| `stringifier` | Factory `() => DriveDataStringify` | Obtain a serializer for each request |
| `receiver` | Direct callback `DriveReceiver<T>` | Called per chunk while consuming the monitored stream |

### Default parser

```ts
const parse = parser();
```

Default behavior follows this priority order:

1. If `response.ok === true`, `response.body !== null`, and a receiver is supplied, provide
   `res.stream` without filling `res.body`;
2. If the response has no body, leave `res.body` as `undefined`;
3. If `Content-Disposition` contains the case-sensitive lowercase substring `attachment`, parse a `Blob`;
4. Parse `application/json` or media types ending in `+json` as JSON; empty content remains `undefined`;
5. Without Content-Type, or when the decoded category matches `isRawTextBody()`, parse text;
6. Leave unrecognized binary types as `undefined` for a `request()` caller or custom parser to handle.

Non-`ok` responses skip receiver mode and continue with the subsequent content-type parsing rules.

Custom parsers use the same signature and are supplied with `parser: () => customParse`. Progress occurs only if they explicitly
read `options.receiver` and construct a monitored stream; Drive does not automatically attach the default
parser's stream logic.

### `DriveBodyParse<T>`

```ts
interface DriveBodyParse<T> {
  (
    response: Response,
    context: DriveContext<T>,
    options?: { receiver?: DriveReceiver<T> },
  ): Promise<void>;
}
```

### `DriveDataStringify`

```ts
interface DriveDataStringify {
  (
    value: unknown,
    replacer?: (this: unknown, key: string, value: unknown) => unknown,
    space?: string | number,
  ): string;
}
```

The call shape is compatible with the function-replacer form of `JSON.stringify`, without its replacer-array overload; the public
contract requires a string result. Non-string results for explicit `json` or plain-object/array `data` cause the Promise
to reject.

### `DriveReceiver<T>`

```ts
interface DriveReceiver<T> {
  (event: {
    loaded: number;
    total?: number;
    done: boolean;
    percentage?: number;
    context: DriveContext<T>;
    value?: Uint8Array;
  }): void;
}
```

`receiver` is a direct callback, not `receiver: () => (event) => { ... }`. TypeScript's permissive assignment rules for
`void` callbacks may allow that incorrect factory form, but Drive does not use its returned
function. Drive treats receivers as synchronous notifications without awaiting return values: synchronous throws
fail `res.stream` reads, while Promises returned by async callbacks are not observed.

The default stream has backpressure: it does not keep pulling without downstream reads. Canceling `res.stream` forwards the reason
upstream. Event-field guarantees:

| Field | Guarantee |
| --- | --- |
| `loaded` | Always present; cumulative bytes read |
| `done` | Always present; `true` for completion events |
| `context` | Always present; current Context |
| `value` | Present on chunk events, absent on completion |
| `total` | Only present for valid `Content-Length` |
| `percentage` | Only present when total size is computable |

## stages

Stages are advanced boundary extensions. If middleware, parser, stringifier, or repeat can express the requirement, there is no need to replace
an entire stage.

### `DriveStagePrepare`

```ts
type DriveStagePrepare = <T>(options: {
  stringify: DriveDataStringify;
  timeout?: number;
}) => DriveMiddleware<T>;
```

Forms a sendable request and merges timeout cancellation into `req.signal` as described above. Replacing it means taking over
these responsibilities.

### `DriveStageSend`

```ts
type DriveStageSend = <T>() => DriveMiddleware<T>;
```

Custom send must supply these fields **before** calling `next()`:

- `context.res.raw: Response`;
- `context.res.status: number`;
- `context.res.headers: Headers`.

If any is missing, inner receive does not run and the request rejects with `TypeError`. `type` and `charset`
are not minimum send requirements; the parser can synchronize them from raw. Calling
`context.decode(response)` writes status, headers, type, and charset, but that Response must still be assigned separately
to `res.raw`. If custom send intentionally omits `next()`, all three fields must still be written before returning;
the [middleware short-circuit contract](#function-signature) applies.

### `DriveStageReceive`

```ts
type DriveStageReceive = <T>(options: {
  parse: DriveBodyParse<T>;
  receiver?: DriveReceiver<T>;
}) => DriveMiddleware<T>;
```

Passes the obtained Response to the current parser to produce a body or stream. Replacing it means deciding
whether and when the parser runs.

## `repeat()`

```ts
declare function repeat(options?: DriveRepeatPolicy): DriveStageSend;
```

repeat is an optional sending policy and a complete `DriveStageSend`. It takes over Fetch sending rather than
wrapping or invoking another custom send. It decides whether to continue only after Fetch returns a Response, without requiring
`response.ok`; responses such as `401`, `429`, and `503` can all reach `eligible`. A rejected Fetch
Promise bypasses this policy and propagates directly.

```ts
interface DriveRepeatPolicy<T = unknown> {
  eligible?: (
    attempt: number,
    snapshot: DriveContextSnap<T>,
  ) => boolean | Promise<boolean>;

  effect?: (
    attempt: number,
    context: DriveContext<T>,
  ) => void | Promise<void>;

  delay?: number | ((
    attempt: number,
    snapshot: DriveContextSnap<T>,
  ) => number);
}
```

| Field | Contract |
| --- | --- |
| `eligible` | Whether to continue after the current response; only strict `true` continues; omission sends once |
| `effect` | Runs after deciding to continue and before the next send; may mutate the original Context |
| `delay` | Milliseconds between sends; number or synchronous function, default `0` |

Observable order: obtain this attempt's Response → create snapshot → `eligible` → `effect` →
`delay` → next send. `attempt` starts at `1` and identifies the just-completed send. Function-form
`delay` receives the same snapshot as `eligible` and cannot see changes made by `effect`.
Response-body decisions belong in `eligible`; function-form `delay` should compute waiting time from snapshot metadata only.

Any synchronous callback throw, or rejected Promise from `eligible` / `effect`, stops repeat. During delay, the current
`AbortSignal` can interrupt waiting. Intermediate response bodies should not remain unconsumed; Drive makes a best effort to cancel them. Only the final
Response reaches receive/parser.

prepare does not rerun before each attempt. `effect` should change the actual next-send fields,
`context.api` or `context.req`; modifying `data`, `query`, or `json` does not re-encode automatically. To
replace a one-shot body, provide a fresh `context.req.body` directly.

Safety requirements:

- Provide a clear stop condition;
- Repeat only safely replayable requests;
- Non-idempotent writes require server-side idempotency guarantees;
- Consumed `ReadableStream` instances cannot be reused; `effect` must supply a new body;
- If `eligible` needs the body, read and promptly consume `snapshot.res.raw.clone()`, not
  the original Response still needed by the parser.

## `isRawTextBody()`

```ts
type RawTextBodyType =
  | "txt"
  | "css"
  | "xml"
  | "html"
  | "plain"
  | "richtext"
  | "javascript";

declare function isRawTextBody(type?: string): type is RawTextBodyType;
```

Determine whether an **already decoded category string** belongs to the default parser's text-readable set. This is not a
MIME parser; supply a category name, not a complete `Content-Type`.

## `toSearchParams()`

```ts
type SearchParamScalar = string | number | boolean | bigint | Date | null;
type SearchParamValue = SearchParamScalar | readonly SearchParamScalar[] | undefined;
type SearchParamsInput =
  | string
  | URLSearchParams
  | Readonly<Record<string, SearchParamValue>>;

function toSearchParams(data: SearchParamsInput): URLSearchParams;
```

Convert query input into independent `URLSearchParams`. Drive's `query` channel still accepts only
`URLSearchParams`; use this helper to construct it from objects or strings. TypeScript interfaces with explicit
properties can also be passed directly.

| Input type | Behavior |
| --- | --- |
| `URLSearchParams` | Copy it; mutating the result does not affect input |
| `string` | `new URLSearchParams(string)` |
| Plain object | Add parameters in property order; read only own enumerable string keys |
| Other inputs, including top-level `string[]` | Throw `TypeError` |

Plain-object values follow these rules: strings, booleans, `bigint`, and finite numbers become strings;
`null` becomes `"null"`; valid `Date` uses ISO format; omit `undefined` and empty arrays;
scalar array entries generate duplicate keys in order. Nested objects, `undefined` array entries, invalid `Date`,
`NaN`, and infinities throw `TypeError`. Serialize explicitly first for JSON or comma-separated formats.

```ts
import { toSearchParams } from "@momots/drive";

toSearchParams("a=1&b=2").get("a"); // => "1"
toSearchParams({
  tags: ["momo", "drive"],
  page: 2,
  unused: undefined,
}).toString(); // => "tags=momo&tags=drive&page=2"

toSearchParams({ filter: JSON.stringify({ tag: "momo" }) });
```
