Each example addresses one concern. When combining them, keep domain APIs simple and place rules shared across endpoints in a common
client. `drive` represents an existing application service client; other undefined identifiers such as `getToken()` and `file`
are application dependencies. These snippets illustrate API composition, not a complete application. The
`/api/...` URLs assume a same-origin browser environment; Bun/Node.js generally require absolute URLs.

## Basic calls at a glance

Prefer explicit fields so data destinations are visible at the call site:

```ts
// query
const users = await drive.get<User[]>({
  api: "/api/users?active=1#results",
  query: new URLSearchParams({ page: "2" }),
});

// JSON
const user = await drive.post<User>({
  api: "/api/users",
  json: { name: "Ada" },
});

// FormData
const form = new FormData();
form.set("avatar", file);
await drive.post<void>({ api: "/api/avatar", body: form });

// Raw text must use body rather than data
await drive.post<void>({ api: "/api/source", body: "plain text" });
```

When the meaning is obvious, positional calls work too:

```ts
const user = await drive.post<User>("/api/users", { name: "Ada" });

const users = await drive.get<User[]>(
  "/api/users",
  new URLSearchParams({ page: "2" }),
  { headers: { "X-View": "compact" } },
);
```

`json` and `body` are mutually exclusive. To send `URLSearchParams` as a form body, place it explicitly in `body`; in
`query` or `data`, it enters the URL. The second positional argument is the automatic `data` channel, with the same semantics as
`{ api, data }`, not a legacy API. Explicit fields remain preferable for complex requests.

Drive preserves fragments while merging query parameters, but URL/Fetch semantics mean fragments are not included in HTTP
requests.

## Build query parameters from an object

`query` accepts only `URLSearchParams`. Use `toSearchParams` to construct it from a plain object:

```ts
import { toSearchParams } from "@momots/drive";

function buildListUrl(params: { page?: number; size?: number; q?: string }) {
  const qs = toSearchParams(params).toString();
  return qs ? `/api/list?${qs}` : "/api/list";
}

buildListUrl({ page: 2, size: 20, q: undefined }); // => "/api/list?page=2&size=20"
```

You can also pass it directly to Drive's `query` channel:

```ts
import { toSearchParams } from "@momots/drive";

const users = await drive.get<User[]>({
  api: "/api/users",
  query: toSearchParams({ page: 2, active: true }),
});
```

## Consistent HTTP status errors

When a service explicitly treats all `4xx` / `5xx` responses as exceptions, define that policy at the service boundary:

```ts
import { Drive } from "@momots/drive";

export const drive = new Drive().use("/api/**", async (context, next) => {
  await next();

  if ((context.res.status ?? 0) >= 400) {
    throw new Error(`HTTP ${context.res.status} @ ${context.path}`);
  }
});
```

Drive does not make this decision itself. If error semantics differ between endpoints, individual
`request()` checks are clearer than global middleware.

## Timeout and manual cancellation

`timeout` adds timeout cancellation to default Fetch; the caller's signal retains application-controlled cancellation:

```ts
const controller = new AbortController();

const request = drive.get<Report>({
  api: "/api/reports/current",
  timeout: 5_000,
  signal: controller.signal,
});

cancelButton.addEventListener("click", () => {
  controller.abort(new Error("User cancelled"));
});

const report = await request;
```

Default prepare combines timeout cancellation into `req.signal` after encoding. Cancellation is cooperative: custom extensions
must observe the signal themselves. It excludes encoding, work in outer middleware, and stream consumption after return. Once the stream reaches the
caller, continue using your own signal to manage its download lifecycle.

## Download large files with progress

Use `request()` to obtain a stream and observe progress without reading the entire response in advance:

```ts
async function download(url: string): Promise<Blob> {
  const context = await drive.request<void>({
    api: url,
    method: "GET",
    receiver: ({ loaded, total, percentage, done }) => {
      updateProgress({ loaded, total, percentage, done });
    },
  });

  if (!context.res.stream) {
    throw new Error(`Expected a stream, received HTTP ${context.res.status}`);
  }

  return new Response(context.res.stream, {
    headers: context.res.headers,
  }).blob();
}
```

Consuming `res.stream` drives reads. Without a valid `Content-Length`, `total` and
`percentage` are absent. Streaming requests cannot use body-only shortcuts or `exec()`.

## Add CSRF headers only to writes

Use the [CSRF recipe](/docs/drive/recipes#csrf) to check origins and add tokens after prepare has finalized the method.
Import its dedicated subpath and configure `stages.send`:

```ts
import { Drive } from "@momots/drive";
import { csrf } from "@momots/drive/recipes/csrf";

export const drive = new Drive({
  stages: {
    send: csrf({
      origin: () => window.location.origin,
      header: () => "X-CSRF-Token",
      token: () => getCsrfToken(),
    }),
  },
});
```

`getCsrfToken()` is application-provided and may return a string or Promise. The recipe covers explicit methods
and automatically inferred POST. An origin mismatch or missing token on a write fails before sending. It occupies
`stages.send` and cannot currently be combined with `repeat`. The server must still validate the token.

## Custom RPC response parsing

Centralize service-specific envelope parsing and error conversion in a parser:

```ts
type RpcResponse<T> = {
  code: number;
  data: T;
  message?: string;
};

const user = await drive.post<User>({
  api: "/api/rpc",
  json: { method: "user.detail", params: { id: "u1" } },
  parser: () => async (response, context) => {
    const body = await response.json() as RpcResponse<User>;
    if (body.code !== 0) throw new Error(body.message ?? "RPC failed");
    context.res.body = body.data;
  },
});
```

`parser` is a factory returning a parsing function. That function writes `context.res.body`; errors it throws
reject the Promise. Type assertions in this example do not validate structure at runtime; call your chosen schema tool
here if envelope validation is needed.

## Isolate service boundaries

Use separate instances to keep tokens, tenant headers, and error policies from leaking across boundaries:

```ts
import { Drive } from "@momots/drive";

export const appDrive = new Drive().use("/api/**", async (context, next) => {
  context.req.headers.set("Authorization", `Bearer ${getAppToken()}`);
  await next();
});

export const reportDrive = new Drive().use(
  "/reports/**",
  async (context, next) => {
    context.req.headers.set("X-Tenant", getTenantId());
    await next();
  },
);
```

Multiple instances express different policy boundaries; they are not intended as one client per endpoint.

## Record complete audit information

Use `request()` when the caller needs the original HTTP result:

```ts
async function audited<T>(api: string): Promise<T | undefined> {
  const context = await drive.request<T>({ api, method: "GET" });

  await saveAuditLog({
    requestId: context.req.id,
    path: context.path,
    status: context.res.status,
    contentType: context.res.headers.get("Content-Type"),
  });

  return context.res.body;
}
```

The returned body is optional. If a domain function promises `Promise<T>`, first check that the
body exists or validate it with a runtime schema.

## Repeat idempotent requests based on response status

After Fetch obtains a `503` response, a safe query can be sent again a limited number of times:

```ts
import { Drive, repeat } from "@momots/drive";

export const reportDrive = new Drive({
  stages: {
    send: repeat({
      eligible: (attempt, snapshot) =>
        attempt < 3 &&
        (snapshot.req.method ?? "").toUpperCase() === "GET" &&
        snapshot.res.status === 503,
      delay: (attempt) => attempt * 200,
    }),
  },
});
```

`eligible` handles only obtained Responses; network failures propagate immediately. Always provide a stopping
condition and ensure the request has no non-replayable body or duplicate side effects.

## Refresh a token after the first 401

Separate the decision to continue from changes to the next request when refreshing tokens:

```ts
import { Drive, repeat } from "@momots/drive";

const authDrive = new Drive({
  stages: {
    send: repeat({
      eligible: (attempt, snapshot) =>
        attempt === 1 && snapshot.res.status === 401,
      effect: async (_attempt, context) => {
        const token = await refreshToken();
        context.req.headers.set("Authorization", `Bearer ${token}`);
      },
    }),
  },
});
```

Errors from `eligible`, `effect`, or `delay` stop repeat. If the decision requires the response body,
read and promptly consume a clone of `snapshot.res.raw`, never the original response.

See the [API reference](/docs/drive/guide) for exact rules.
