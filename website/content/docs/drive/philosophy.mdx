Drive divides request code into three parts: endpoint functions choose URLs, data, and expected results; client middleware
handles rules shared by multiple endpoints, such as authentication, logging, and error conversion; headers, cancellation, bodies, and streams retain Fetch's
semantics.

## Where shared rules belong

For a few unrelated requests, direct `fetch()` calls are enough. As endpoints increase, the same rules appear
repeatedly: where tokens go, which paths need auditing, who interprets status codes, and when raw responses must be retained.

Scattering these rules across pages and domain functions requires finding every call site for each change. Putting everything in one global client lets one
domain's rules affect other domains. Drive keeps each domain function focused on its own request and attaches
shared rules to a client with an appropriate scope.

## Endpoint functions and clients

A domain endpoint function needs to specify only three things: the URL, whether data goes into query parameters or the body, and the result the caller
receives. Authentication, logging, tenant identifiers, and uniform error conversion apply to groups of requests, not individual endpoints.

Organize code into two layers:

- Domain APIs: one function per business action, passing data through `query`, `json`, or `body`;
- Service clients: register middleware shared by multiple endpoints.

`query`, `json`, and `body` show the data destination at the call site. `data` selects a channel automatically based on
the value's type; the second positional argument also maps to `data`. These forms offer the same capabilities and remain supported;
choose whichever reads most clearly in context.

## Scope rules with clients

A client usually represents a service boundary: requests sharing transport rules, grouped by domain name, backend service, or
authentication method. Middleware attached to one client does not affect requests from another.

Within a client, middleware can match paths or filter by predicate. Paths describe business scope, such as
`/admin/**`; predicates express conditions paths cannot, such as applying only to `POST` requests.

Two useful guidelines:

- Each middleware handles one concern, such as writing a token or recording audit information;
- Each domain function relies only on its own client's middleware, not other domains' rules.

## Retain Fetch types and limitations

Drive does not invent a new request object. Headers remain `Headers`, cancellation uses `AbortSignal`, raw responses are
`Response`, and files, forms, and streams follow Fetch body and `ReadableStream` rules.

Existing Fetch knowledge applies directly, as do its limitations: relative URLs require a runtime base,
GET/HEAD requests cannot have bodies, and a consumed stream does not become replayable by passing through Drive.

## When to return Context

Middleware reads and writes requests and responses through one shared Context. Domain code usually needs only the parsed result, not the entire
Context.

Domain functions therefore normally use shortcuts or `exec()`, returning only `res.body`. When status, headers,
the raw response, or streams are needed, use `request()` for the full Context.

Predicates and repeat's `eligible` and `delay` read snapshots, so their decisions cannot mutate the request itself.
Use `effect` to modify the original Context for the next repeat attempt.

## Let the domain decide failure and replay

The same HTTP status may mean different things in REST, GraphQL, and asynchronous jobs. Drive therefore does not automatically turn
`4xx` / `5xx` into exceptions or check whether response JSON matches the generic `T`.

Drive also does not manage caching or UI loading state, or determine replay safety. `repeat` only sends again after obtaining a
Response; callers decide when to stop, whether requests are idempotent, and how to reconstruct one-shot bodies.

Define shared error or replay rules as middleware in the corresponding client; if only one endpoint needs a rule, keep it in that
domain function.

## Designing the request layer

Answer three questions in order:

1. Which requests share transport rules and belong in the same client?
2. Which rules span endpoints, and which belong to a single endpoint?
3. Does the caller need only the parsed result, or also status, headers, or streams?

The first determines the number of clients, the second determines middleware ownership and path matching, and the third determines
whether to use shortcuts or `request()`. Keep a rule in its domain function until its intended request scope is clear.
