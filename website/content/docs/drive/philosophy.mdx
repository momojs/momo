Drive 的核心判断是：**接口函数说明业务想做什么，客户端说明哪些传输规则适用，Fetch
负责平台层的网络语义。**

这套设计关注的不是如何少写一次 `fetch()`，而是接口增多之后，鉴权、日志、错误转换等
规则应该放在哪里，才能保持清楚、可组合且互不泄漏。

## 要解决的是规则归属

少量独立请求通常不需要额外抽象。真正让请求层变复杂的，是同一规则开始出现在多个
接口里：令牌要写在哪里、哪些路径需要审计、谁负责解释状态码、何时必须保留原始响应。

如果这些决定散落在页面和领域函数中，修改一项策略就需要追踪许多调用点；如果全部塞进
一个全局客户端，又会让无关业务域彼此影响。

Drive 的目标是在两者之间建立明确边界：领域函数保持具体，公共策略按适用范围集中。

## 业务意图与传输策略分开

领域接口最重要的信息只有三类：目标是什么、数据要去哪里、调用方需要什么结果。鉴权、
日志、租户标识和统一错误转换则描述一组请求共同遵守的规则，不属于某个具体业务动作。

Drive 因此鼓励两层结构：

- 领域 API 负责给请求命名，并表达查询参数、JSON 或原生请求体的用途；
- 服务客户端负责承载跨接口复用的传输策略。

显式的 `query`、`json`、`body` 是为了让意图在调用处可见。自动 `data` 与位置式调用则
服务于更紧凑的表达；它们不是旧接口，也不是另一套语义。选择哪种写法取决于哪一种更
容易被当前代码的读者理解。

这项分工让领域代码不必知道中间件如何组织，也让传输策略不必了解页面状态或具体业务
模型。

## 用服务边界控制策略范围

一个客户端通常对应一个服务边界，也就是共享同一组传输规则的请求集合。域名、后端服务
或认证规则都可以成为划分依据。边界内的请求共享规则，边界外的请求不会被意外影响。

路径适合表达稳定的业务范围，谓词适合补充方法或请求元数据等条件。两者的目的都不是
复制路由系统，而是回答同一个问题：**这项策略为什么应当作用于这组请求？**

好的边界通常具有两个特征：

- 一项策略只有一个清楚的职责，例如写入令牌或记录审计信息；
- 一个领域函数只依赖服务客户端的公共约定，不依赖其他业务域的策略。

这也是 Drive 对高内聚、低耦合的理解：相关规则靠近所属边界，无关规则通过不同客户端
隔离。

## 保留 Fetch 的平台语义

Drive 不用私有对象替代 Fetch 已经定义的概念。请求头仍是 `Headers`，取消仍由
`AbortSignal` 表达，原始响应仍是 `Response`，文件、表单和流仍遵循平台的 body 与
`ReadableStream` 规则。

这样做有两个结果。第一，已有的 Fetch 知识可以直接复用；第二，平台限制也不会被隐藏。
例如相对 URL 是否有效取决于运行时是否有基址，GET/HEAD 请求体仍受 Fetch 限制，已经
消费的流也不会因为经过 Drive 就自动变得可重放。

Drive 提供的是编排能力，而不是另一套网络协议。

## 让 Context 停留在传输边界

中间件需要同时观察请求与响应，Context 为它们提供共同语言；领域代码通常只需要解析后
的结果，不应被迫理解整份传输状态。

因此，领域函数通常使用快捷方法或 `exec()` 直接返回结果；只有确实需要状态码、响应头、
原始响应或流时，才改用 `request()`。这样不必让所有接口都返回 Context。

谓词和 repeat 的判断读取快照，避免判断过程顺手改动请求；repeat 需要更新下一次发送时，
再由 `effect` 修改原 Context。读与写因此有清楚的分工。

## 不替业务定义失败与可重放性

HTTP 状态不等同于业务结果。REST、GraphQL 和异步任务可能对同一个状态码作出不同解释，
所以 Drive 默认不把 `4xx` / `5xx` 转换成异常，也不推断响应 JSON 是否满足泛型 `T`。

同理，Drive 不替应用决定缓存、UI 加载状态或请求是否可以安全重放。`repeat` 只提供在已
取得 Response 后再次发送的机制；停止条件、幂等保障和一次性请求体的重建仍属于业务
策略。

这些选择看似保守，却避免了客户端在没有足够上下文时替业务做决定。需要统一规则时，
应用可以在服务边界集中定义；需要个别处理时，则保留在领域函数中。

## 如何应用这套思路

设计请求层时，依次回答三个问题：

1. 哪些请求属于同一个服务边界？
2. 哪些规则被多个接口共享，哪些只是单个业务动作的决定？
3. 调用方只需要领域结果，还是确实需要 HTTP 元数据或流？

答案会自然决定客户端数量、中间件范围和返回入口。若一项规则无法说明自己的适用边界，
它通常还不适合被提升为公共策略。
