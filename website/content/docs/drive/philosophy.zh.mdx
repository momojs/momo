Drive 把请求代码分成三部分：接口函数决定请求地址、数据和期望的结果；客户端上的中间件
处理鉴权、日志、错误转换等多个接口共用的规则；请求头、取消、请求体和流仍按 Fetch 的
规则处理。

## 公共规则放在哪里

只有少量互不相关的请求时，直接用 `fetch()` 就够了。接口变多以后，同一条规则会出现在
多个接口里：令牌写在哪里、哪些路径需要审计、谁来解释状态码、何时必须保留原始响应。

这些规则写在页面和领域函数里，改一条就要找遍所有调用点；全部放进一个全局客户端，一个
业务域的规则又会作用到其他业务域的请求上。Drive 的做法是让领域函数只写自己的请求，把
共用规则按适用范围挂到客户端上。

## 接口函数与客户端

一个领域接口函数只需要说明三件事：请求哪个地址、数据放在查询参数还是请求体、调用方
拿到什么结果。鉴权、日志、租户标识和统一错误转换适用于一组请求，不属于某个具体接口。

因此建议分两层组织代码：

- 领域 API：每个函数对应一个业务动作，用 `query`、`json` 或 `body` 传数据；
- 服务客户端：注册多个接口共用的中间件。

`query`、`json`、`body` 让读代码的人在调用处就能看出数据去向。`data` 会按值的类型自动
选择通道，位置式写法的第二个参数也映射到 `data`。几种写法能力相同，都可以长期使用，
按哪种在当前代码里更易读来选。

## 用客户端划分规则范围

一个客户端通常对应一个服务边界，即共享同一组传输规则的请求，可以按域名、后端服务或
认证方式划分。挂在一个客户端上的中间件不会作用于其他客户端发出的请求。

同一个客户端内，中间件可以按路径匹配，也可以用谓词筛选。路径适合划分业务范围，例如
`/admin/**`；谓词用于路径表达不了的条件，例如只对 `POST` 请求生效。

划分时可以参考两点：

- 一个中间件只处理一件事，例如写入令牌或记录审计信息；
- 一个领域函数只依赖所在客户端的中间件，不依赖其他业务域的规则。

## 保留 Fetch 的类型和限制

Drive 不另造请求对象。请求头仍是 `Headers`，取消用 `AbortSignal`，原始响应是
`Response`，文件、表单和流仍按 Fetch 的 body 与 `ReadableStream` 规则处理。

所以已有的 Fetch 知识可以直接用，Fetch 的限制也照样存在：相对 URL 是否有效取决于运行时
有没有基址，GET/HEAD 请求不能带请求体，已经读过的流不会因为经过 Drive 就能重新发送。

## 何时返回 Context

中间件通过同一个 Context 读写请求和响应。领域代码通常只需要解析后的结果，用不到整个
Context。

所以领域函数一般用快捷方法或 `exec()`，它们只返回 `res.body`。需要状态码、响应头、
原始响应或流时，再改用返回完整 Context 的 `request()`。

谓词，以及 repeat 的 `eligible` 和 `delay`，读取的都是快照，判断过程改不到请求本身。
repeat 需要修改下一轮请求时，在 `effect` 里修改原 Context。

## 失败与重放由业务决定

同一个 HTTP 状态码在 REST、GraphQL 和异步任务里可能含义不同，所以 Drive 默认不把
`4xx` / `5xx` 转成异常，也不检查响应 JSON 是否符合泛型 `T`。

Drive 也不处理缓存和 UI 加载状态，不判断请求能否安全重放。`repeat` 只负责在拿到
Response 后再次发送请求；何时停止、请求是否幂等、一次性请求体如何重建，由调用方决定。

需要统一的错误或重放规则时，在对应客户端里用中间件定义；只有个别接口需要时，写在该
领域函数里。

## 设计请求层时

依次回答三个问题：

1. 哪些请求共用一组传输规则，应该放进同一个客户端？
2. 哪些规则被多个接口共用，哪些只属于单个接口？
3. 调用方只需要解析后的结果，还是需要状态码、响应头或流？

第一个问题决定客户端数量，第二个决定中间件挂在哪个客户端、匹配哪些路径，第三个决定用
快捷方法还是 `request()`。说不清该作用于哪些请求的规则，先留在领域函数里。
