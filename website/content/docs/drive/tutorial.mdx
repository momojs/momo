This tutorial establishes a clear request boundary for a user service. When finished, pages call only domain functions,
shared transport rules live in the client, and `request()` is used explicitly when HTTP metadata is needed.

The `/api/...` examples assume a same-origin browser environment. Drive has no `baseURL`; Bun and Node.js generally require
absolute URLs. Undefined identifiers such as `getToken()` represent application dependencies.

## Step 1: Create a service client

Create a Drive instance in a separate module. An instance usually represents one service boundary, such as requests sharing a domain name, backend service,
or authentication policy.

```ts
// api/client.ts
import { Drive } from "@momots/drive";

export const drive = new Drive();
```

Keep the client simple initially. Promote a rule here only when multiple endpoints need it.

## Step 2: Name requests with domain functions

Pages should not repeatedly assemble URLs and options. Encapsulate those details in APIs named after business actions:

```ts
// api/users.ts
import { drive } from "./client";

export type User = { id: string; name: string };
export type CreateUser = { name: string };

export const UserApi = {
  list: (page: number) =>
    drive.get<User[]>({
      api: "/api/users",
      query: new URLSearchParams({ page: String(page) }),
    }),

  create: (input: CreateUser) =>
    drive.post<User>({ api: "/api/users", json: input }),

  remove: (id: string) =>
    drive.delete<void>({ api: `/api/users/${id}` }),
};
```

Function names express domain actions; `query` and `json` express data destinations; generics express the backend contract the caller
expects. Drive does not validate `User` at runtime; add a schema or custom
parser.

## Step 3: Choose the clearest data form

Object-style APIs expose three explicit channels:

| Field | Intent |
| --- | --- |
| `query` | Merge `URLSearchParams` into the URL |
| `json` | Send a structured value as a JSON body |
| `body` | Pass a native Fetch `BodyInit` through unchanged |

Simple calls can also use positional arguments:

```ts
const created = await drive.post<User>(
  "/api/users",
  { name: "Ada" },
  { timeout: 5_000 },
);
```

This has the same capabilities as `{ api, data, ...init }`: the second argument is simply the automatic `data` channel. Plain objects and arrays
become JSON, `URLSearchParams` goes into the URL, and supported native body objects pass through to Fetch.

For public APIs or complex requests, prefer `query`, `json`, and `body` so readers need not infer destinations from value
types. Strings, `Date`, `Map`, and custom classes should not be passed directly as `data`. Do not declare the same channel through both automatic and explicit
fields; see [API reference · Channel conflicts](/docs/drive/guide#channel-conflicts) for exact combinations.

## Step 4: Choose the return entry point

| Need | Entry point | Return |
| --- | --- | --- |
| Standard HTTP method, parsed result only | Shortcuts such as `get()` and `post()` | `T` |
| Custom method, parsed result only | `exec()` | `T` |
| Status, headers, raw Response, or streams | `request()` | Full Context |

For example, use `get()` when a detail query only needs `User`; interpreting `404` as “not found” requires the status:

```ts
export async function findUser(id: string): Promise<User | undefined> {
  const context = await drive.request<User>({
    api: `/api/users/${id}`,
    method: "GET",
  });

  if (context.res.status === 404) return undefined;
  if (context.res.status >= 400) {
    throw new Error(`HTTP ${context.res.status}`);
  }
  return context.res.body;
}
```

When `request()` succeeds, `raw`, `status`, and `headers` always exist; whether `body` exists depends on the
response and parser. Drive does not reject automatically for `4xx` / `5xx`.

The `T` on shortcuts and `exec()` is only a caller assertion and does not select the parser at runtime. Use `void` for a known empty
body and `T | undefined` when the body may be absent.

## Step 5: Promote only shared rules

Suppose all user endpoints need a token and every service request needs auditing. These rules now cross several domain
functions and belong in the client:

```ts
// api/client.ts
export const drive = new Drive()
  .use("/api/**", async (context, next) => {
    context.req.headers.set("Authorization", `Bearer ${getToken()}`);
    await next();
  })
  .use("*", async (context, next) => {
    const startedAt = performance.now();
    await next();
    recordRequest({
      path: context.path,
      status: context.res.status,
      duration: performance.now() - startedAt,
    });
  });
```

Handle requests before `await next()` and responses afterward. Paths only determine where rules apply; pages still depend solely on
`UserApi` and never see token or audit details.

The basic client is now complete: domain functions describe business actions, explicit channels describe data intent, service clients
centralize shared policies, and `request()` appears only when HTTP information is needed.

## Add capabilities as needed

The following features are optional additions, not prerequisites for a basic client. Add them when required and first identify the appropriate
layer:

| Need | Approach | Read more |
| --- | --- | --- |
| Timeout cancellation for default Fetch, or user cancellation | `timeout` with a caller `AbortSignal` | [Timeouts and cancellation](/docs/drive/examples#timeout-and-manual-cancellation) |
| Download large files with progress | `request()`, `receiver`, and the returned stream | [Streaming downloads](/docs/drive/examples#download-large-files-with-progress) |
| Interpret HTTP statuses consistently | Middleware at an explicit service boundary | [Status errors](/docs/drive/examples#consistent-http-status-errors) |
| Parse a service-specific response envelope | A parser for that boundary | [Custom parser](/docs/drive/examples#custom-rpc-response-parsing) |
| Send again based on an obtained response | A repeat policy with stop conditions and idempotency guarantees | [Response-based repeat](/docs/drive/examples#repeat-idempotent-requests-based-on-response-status) |

See [examples](/docs/drive/examples) for complete scenarios; the authoritative definitions of fields, overloads, matching order, and lifecycle are in the
[API reference](/docs/drive/guide).
