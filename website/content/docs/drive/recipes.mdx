These optional recipes are officially maintained and tested. Import each from its dedicated package subpath as needed, then connect it through
Drive's extension points.

## CSRF

This recipe targets browser APIs using cookie sessions with server-side CSRF token verification.
It runs after `prepare`, reading the encoded request and final method, so it also covers automatically inferred
POST. Since `0.1.0-beta.1`, it is available from `@momots/drive/recipes/csrf`.

### Setup

Configure `stages.send` on your service client:

```ts
import { Drive } from '@momots/drive';
import { csrf } from '@momots/drive/recipes/csrf';

export const api = new Drive({
  stages: {
    send: csrf({
      origin: () => window.location.origin,
      header: () => 'X-CSRF-Token',
      token: () =>
        document.querySelector<HTMLMetaElement>(
          'meta[name="csrf-token"]',
        )?.content,
    }),
  },
});

// prepare encodes json and infers POST, so the token is added too.
await api.request({
  api: '/api/profile',
  json: { nickname: 'mango' },
});
```

This example assumes the server supplies a token in HTML `meta[name="csrf-token"]` and validates the request's
`X-CSRF-Token`. Match the header name and token source to the backend's existing CSRF implementation.

The same subpath exports the `CsrfOptions` type and `CsrfTokenMissingError` class:

```ts
import type { CsrfOptions } from '@momots/drive/recipes/csrf';
import { CsrfTokenMissingError } from '@momots/drive/recipes/csrf';
```

### Options and evaluation timing

| Option | Type | Behavior |
| --- | --- | --- |
| `origin` | `Realizable<string>` | Required string or synchronous no-argument function, evaluated once before each send |
| `header` | `Realizable<string>` | Defaults to `X-CSRF-Token`; evaluated once per send after origin validation |
| `token` | `({ signal }) => string \| null \| undefined \| Promise<string \| null \| undefined>` | Called again for every protected request; sending waits for its result |

`Realizable<string>` comes from `@momots/core` and means `string | (() => string)`. Resolvers are not run when creating
the client, so later requests can read updated application configuration. Keep `origin` and `header` resolvers
synchronous and put asynchronous work in `token`.

`origin` is a complete HTTP(S) origin such as `https://api.example.com`; paths, queries,
fragments, and credentials are rejected. Comparison uses URL-normalized protocol, host, and port, without matching subdomains.
It restricts the initial destination and is not a base for relative URLs.

In browsers, relative URLs resolve against `document.baseURI`, including a page's `<base>` setting; the resolved origin is checked
and the absolute URL is sent. Bun, Node.js, and environments without a document base should supply
absolute URLs. Use trusted application configuration for the origin, not a value inferred from the current request URL.

### Asynchronous tokens

`token` may be an `async` function or return a Promise directly. This example assumes a read-only server
`GET /api/csrf` endpoint returning `{ token: string }`:

```ts
const api = new Drive({
  stages: {
    send: csrf({
      origin: () => window.location.origin,
      header: 'X-CSRF-Token',
      token: ({ signal }) =>
        fetch('/api/csrf', { signal, credentials: 'same-origin' })
          .then(async (response) => {
            if (!response.ok) throw new Error('Could not load CSRF token');
            const data = await response.json() as { token?: string };
            return data.token;
          }),
    }),
  },
});
```

The example uses a separate Fetch call to obtain the token. Applications may read their own session state or shared Promise instead;
caching, deduplication, and refresh timing belong to the application. Do not recursively call this client's protected endpoints from the token function.

`signal` is the signal formed by default prepare from manual cancellation and timeout. Observe it during asynchronous acquisition; if a
Promise ignores the signal, cancellation cannot force it to settle, but sending will still stop after it finishes.
Promise rejection preserves the original error.

### Sending rules

| Condition | Result |
| --- | --- |
| Destination does not match configured origin | Throw `TypeError` before sending, without reading the token; GET also checks origin |
| `GET`, `HEAD`, `OPTIONS` | Do not read or automatically add a token; preserve existing headers |
| Other methods, including custom methods and automatic POST | Read token, replace the configured header, then send |
| Token is `null`, `undefined`, empty, or whitespace-only | Throw `CsrfTokenMissingError`; an existing matching header cannot bypass this |
| Protected request, or safe method with the configured token header already set | Force `redirect: 'error'`; do not follow redirects automatically |
| Token required with `mode: 'no-cors'` | Throw `TypeError` before sending |
| Custom prepare did not determine the method | Throw `TypeError` before sending |
| Server returns a status such as 403 | Continue normal Drive parsing; application decides how to handle it |

The recipe uses `context.api` at send time, so it checks destinations rewritten by outer middleware rather than the
`url` or `path` cached when Context was created. The URL, method, and
headers are fixed before awaiting the token; changes to the original Context during that wait do not alter this send's destination.

Requests carrying tokens prohibit redirects so origin checks cover the actual destination. Safe requests without
that header retain their redirect setting. See Fetch redirect rules in
[Fetch Standard](https://fetch.spec.whatwg.org/#http-redirect-fetch).

### Combining with other configuration

Ordinary middleware, parsers, receivers, manual cancellation, and default timeouts still follow Drive's contracts.
`credentials` follows request configuration; applications choose credentials and server CORS
configuration for cross-origin cookie requests.

`csrf()` and `repeat()` both return `DriveStageSend`; only one `stages.send` can currently be selected.
Specifying `stages.send` on an individual request overrides the instance configuration and replaces this recipe. This version does not provide
automatic token refresh or retries.

Servers must validate tokens on protected requests; adding a client header does not replace server-side protection.
Prefer the backend framework's existing CSRF mechanism; see
[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
